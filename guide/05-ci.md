# Stage 5: CI, boot tests, installer tests, real hardware

[Index](README.md) · Previous: [Stage 4b](04b-packages-per-os.md) · Next: [Stage 6: release and publish](06-release-and-publish.md)

Nobody should build or test releases by hand. Jenkins builds every
change, boots what it built, installs it, and publishes only what passed.
People fix failures; they do not run steps.

## What the templates ship

Each OS template has its own `Jenkinsfile` (the `ci-templates`
repository is still a placeholder). The stages:

| Template | Stages |
|----------|--------|
| FreeBSD | Validate, Prepare, Test, Build, Boot test, Archive |
| NetBSD | Validate params, Build, Boot test, Archive |
| OpenBSD | Validate params, Build site set, Media, Boot test (work in progress), Archive |
| DragonFly | Validate params, Test, Build, Boot test, Archive |

Shared ideas, in the templates as noted:

- `PRODUCT_CONF` is a **file parameter** (needs the File Parameter plugin;
  the pipeline unstashes it with `stashedFile`). Every free-text parameter
  is checked against a strict pattern before use: parameters end up in
  file names, VM names and shell commands.
- **Test** (FreeBSD and DragonFly pipelines) runs `tests/run-tests.sh`
  first. A tree that fails its own checks never produces an image. The
  suite includes a leak check for private addresses and names. The
  NetBSD and OpenBSD pipelines have no Test stage yet: add one.
- **Build** runs `build.sh` on the agent or inside a build VM.
- **Boot test** runs `tests/boot-test.sh IMAGE PROFILE NAME` per profile.
- **Archive** keeps `out/**/*.img`, `out/**/*.iso` (FreeBSD,
  DragonFly) and `out/SHA256`; NetBSD has no ISO to keep, and OpenBSD
  keeps the site sets, the redacted `install.conf` and `SHA256`.
- `post { always }` destroys every VM the run created (their names are
  written to a list *before* each VM is created). The FreeBSD pipeline
  also **fails the build if a destroy fails**, so a leaked VM is never a
  green run; the NetBSD, OpenBSD and DragonFly pipelines ignore a failed
  destroy (`|| true`). Make yours fail.

## The VM layer: ci/vm.sh and providers

Every VM goes through `ci/vm.sh`, which dispatches to a provider:

```sh
ci/vm.sh create  NAME IMAGE     # start a VM from IMAGE
ci/vm.sh console NAME           # print the path of its serial console log
ci/vm.sh addr    NAME           # print its address
ci/vm.sh destroy NAME           # stop and remove it
```

The provider is `ci/providers/$WTFBSD_VM_PROVIDER.sh` (the reference is
`bhyve`), or a script of your own named by `WTFBSD_VM_PROVIDER_PATH`.
`NAME` matches `^[a-z][a-z0-9-]{0,30}$`; stdout carries only the answer
(progress goes to stderr). In the FreeBSD template the exit codes are 0
ok, 1 bad arguments, 2 no provider, 3 provider failed; the other
templates' `ci/vm.sh` headers list their own. An unknown provider fails
closed.

The provider runs as root on the agent, so treat it as trusted code: owned
by root, not writable by anyone who can submit a job.

The reference provider uses stock `bhyve(8)` with UEFI firmware from the
`edk2-bhyve` package, a virtio disk, a tap on `bridge0`, and the serial
console on an `nmdm(4)` pair copied to `console-logs/NAME.log`. Host
preparation on FreeBSD:

```sh
pkg install edk2-bhyve
kldload vmm
kldload if_bridge
kldload if_tap
ifconfig bridge0 create
ifconfig bridge0 up
```

To use another hypervisor (QEMU, a cloud API), write a provider with the
same four subcommands. Nothing else changes.

## The boot test

```sh
sh tests/boot-test.sh out/appliance/examplebsd-appliance-amd64.img appliance
```

It waits for `login:` on the serial console (default 600 s, set with
`BOOT_TIMEOUT` on FreeBSD and `WTFBSD_BOOT_TIMEOUT` on the others); for
`appliance` it also waits for sshd on port 22. An optional third
argument names the VM. It always destroys the VM; the FreeBSD script
also exits non-zero when the destroy fails.

Limits today, which your fork should close:

- The **desktop** profile passes on the serial login prompt alone. The
  greeter is not checked yet. Add a screenshot of the VM framebuffer (bhyve
  `fbuf` over VNC, or a QEMU `screendump`) and fail unless the greeter is
  visible.
- The boot test boots the **raw image**. It does not test the ISO or the
  installer. See the next section.

## Installer end-to-end test: test the media you ship

The image that passes CI must be the image users download, and the test
must take the path users take: boot the ISO, install to an empty disk,
reboot from the disk without the ISO, log in.

- **Unattended answers.** FreeBSD: the ISO runs `<slug>-install`, which
  takes `-d disk -u user -k keyfile -y`. OpenBSD: `autoinstall(8)` with the
  `install.conf` the build writes. Generate a fresh SSH key per run and
  delete it afterwards.
- **Attach the ISO as a CD**, not as a disk. UEFI may report "no bootable
  device" for an ISO attached as a disk, and may boot an attached hard
  disk ahead of a new ISO, so it looks like the old image.
- **Reboot from disk only**: detach the ISO, or set the disk first in the
  boot order.
- **What a pass means**: the installer reported success; the installed
  system (not the installer) boots to `login:`; SSH with the per-run key
  works (appliance); the greeter is on screen (desktop); the root
  filesystem is the one you chose (check it on the installed system:
  `mount -p | awk '$2 == "/" { print $3 }'` on FreeBSD).
- **Serial input is slow**: long bursts lose characters and the Enter.
  Send short chunks with pauses. A timeout right after a long write is a
  harness bug before it is an image bug.
- **Screenshots**: capture every installer page, read their sizes with a
  tool (not by eye), and fail if any widget is off screen at the smallest
  resolution you support.
- **Failure paths are tests too**: a disk that is too small, a cancelled
  dialog. The installer must recover without a reboot.
- **Memory**: a graphical install in a VM needs several GiB; a too-small VM
  looks like a hang.

## Real hardware

VMs cannot prove GPU drivers, firmware loading or Wi-Fi association. Add
a stage on a Jenkins agent label that owns real machines:

- a machine with the GPUs and Wi-Fi cards you claim to support, a serial
  console (or IPMI serial-over-LAN) and remote power control;
- the stage writes the image to a test disk, boots it once, and collects
  the serial log and a screenshot (from a capture device, or `xwd -root`
  inside the session);
- the checks: the GPU kernel driver loaded and `/dev/dri` exists (FreeBSD),
  the firmware the driver asked for was found (no firmware load errors in
  `dmesg`), the Wi-Fi interface exists, the greeter is on screen;
- never claim a platform works unless it booted there. Release notes say
  which hardware was tested and which was not.

Real-hardware stages run unattended like the others. They may run less
often (nightly, and before a release) if the machines are shared.

## Rebuild media whenever packages change

The package job and the media job are separate, and the media job reads
the published repository. Chain them:

1. package build green, then publish (always: see [Stage 4](04-packages.md));
2. the publish triggers the media job (a downstream `build job:` step, or
   an upstream trigger on the media job);
3. the media job builds, boot-tests and installer-tests the new images;
4. a green media run goes to [Stage 6](06-release-and-publish.md).

Also trigger the media job when upstream publishes a security fix for a
package on the media, and on a schedule, so the images never fall far
behind the repositories.

## CI lessons

- **Stale results look like fresh ones.** After triggering a build, wait
  for a build number higher than the last one you saw; a queue id is not
  a build number.
- **A check that found nothing must be forced to find something once.**
  Run it against a known-bad input before trusting a green.
- **A skipped package is not a built package.** A bulk build can exit
  green with your package skipped. Check the list of built packages, not
  the exit status.
- **`timeout` does not stop bhyve**; it ignores SIGTERM. Use
  `timeout -k 10 N` and destroy the VM with `bhyvectl --destroy --vm=NAME`
  in cleanup.
- **An aborted build can leave poudriere running.** Check for leftover
  processes and mounts before the next bulk.
- **A job that has never run is untested**, not configured.
- **Locks need timeouts.** A lock held by a hung job stalls everything
  behind it.
- **Secrets only through Jenkins credentials**, read inside single-quoted
  `sh` blocks so Groovy never interpolates them, and never echoed.

## Check that it worked

- A push to the product repository starts a build without anyone
  clicking.
- A deliberately broken overlay file fails the Test or Boot test stage.
- After a run, `ci/vm.sh` providers show no VMs left over.
- A package publish starts a media build by itself.
